# 效能調校紀錄

測試環境：Intel Core Ultra 7 265K（20 執行緒）、RTX 5060 Ti、螢幕 2560×1440，輸出 1280×720 @ 30fps。

## 每幀 CPU 成本拆解（2026-10-14 實測）

| 階段 | 調整前 CPU | 調整後 CPU | 備註 |
| --- | --- | --- | --- |
| dxcam BGRA→RGB 色彩轉換（全解析度） | ~12.8 ms | ~3.3 ms | `cv2.setNumThreads(1)` |
| 從 dxcam 取出畫面副本 | ~2.2 ms | ~0.5 ms | 重複使用預先配置的緩衝區 |
| 縮放 2560×1440→1280×720 | ~8.8 ms | ~1.5 ms | `cv2.setNumThreads(1)` |
| RGB→YUV 轉換 + libx264 veryfast crf23 | ~16 ms | ~16 ms | 未變動 |

端對端（auto_pause 關閉、畫面持續變化、各跑 20 秒）：整個程序從約 **100–114%** 的單核 CPU 降到約 **56–58%**，影格數相同。

## 關鍵發現

- **OpenCV 執行緒池會空轉**：預設使用 20 條執行緒時，`cvtColor`／`resize` 實際只花 1–2 ms，CPU 時間卻是 9–13 ms。設成單執行緒後，CPU 時間降為原本的 1/4～1/6，輸出逐位元相同（已驗證 1280×720、1920×1080、1366×768 三種縮放）。這個設定是整個程序共用的，所以 dxcam 擷取執行緒裡的色彩轉換也會一起受益。
- **每幀配置 11 MB 新陣列很慢**（page fault）：改用 `get_latest_frame(copy=False)` 搭配 `np.copyto` 複製到重複使用的緩衝區。dxcam 的環形緩衝區預設有 8 格，讀到的那一格要再過約 7 幀才會被覆寫，複製只需 0.5 ms，因此很安全。此 API 需要 dxcam ≥ 0.3。
- **沒有採用的方案**：
  - dxcam 直接輸出 BGRA 交給編碼器：省下 cvtColor，但 swscale 從 bgra 轉換反而更慢，整體沒有好處。
  - 限制 x264 執行緒數（threads=4）：CPU 幾乎沒變，位元率卻會改變。
  - 暫停時停止 dxcam：靜態畫面時 dxcam 只複製上一幀（約 0.5 ms／幀），省下的很少，卻多了重新啟動失敗的風險。

## NVENC 硬體編碼（尚未採用）

在合成的捲動畫面上，以同一份無損參考影片比對：

| 編碼器 | CPU／幀 | 位元率 | PSNR | SSIM | VMAF |
| --- | --- | --- | --- | --- | --- |
| libx264 veryfast crf23（目前） | 16.3 ms | 1.07 Mbps | 41.08 | 0.9924 | 99.98 |
| h264_nvenc p5 hq vbr cq23 | 5.1 ms | 1.54 Mbps | 51.31 | 0.9978 | 99.99 |
| h264_nvenc p5 hq vbr cq20 | 4.5 ms | 2.19 Mbps | 53.55 | 0.9985 | 99.99 |

所有品質指標都不比 x264 差，但檔案大約多 40%，而且錄影過程要依賴 GPU 驅動（例如驅動更新或 GPU 重置時，編碼可能在錄影途中失敗）。
